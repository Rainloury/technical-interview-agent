# ADR-0003：面试截止时间由服务端权威控制

| 项目 | 内容 |
| --- | --- |
| 状态 | `accepted` |
| 日期 | 2026-10-17 |
| 决策者 | 项目负责人 |
| 评审日期 | 2026-10-17 |
| 影响 | 面试开始、提交、恢复、报告 |

## 背景

需求要求整场面试 40 分钟硬截止，离线期间继续计时，客户端时间不能延长面试。如果依赖浏览器倒计时或客户端 `submitted_at`，用户可以篡改时间或重放请求。

## 决策

- 面试进入 `in_progress` 时写入 `deadline_at = database_now + interval '40 minutes'`；固定时长 2400 秒，不读取应用实例或客户端时钟。
- 每次提交回答和追问操作都在事务内读取 PostgreSQL 的 `statement_timestamp()` 作为 `server_now`，并与 `deadline_at` 比较。
- 截止有效的唯一条件是 `server_now < deadline_at`；`server_now = deadline_at` 即已截止，不接收新回答或追问。
- `client_submitted_at` 只用于诊断和展示，不参与截止判断、幂等比较或状态迁移。
- 客户端只展示服务端返回的剩余时间，不能通过修改本机时间延长面试。
- 到达截止后，新提交返回 `interview_time_expired`，整场进入或保持 `timed_out`。
- 截止前已接收回答继续评分；未作答轮次标记为 `unanswered`，不写错题。
- 恢复请求不能修改 `deadline_at`，也不能把终态回退。
- 超时扫描与回答提交必须锁定同一条面试记录（`SELECT ... FOR UPDATE`），再读取数据库时间并执行 `WHERE state = 'in_progress'` 条件更新，避免二者并发时互相覆盖。

## 替代方案

- 客户端倒计时：实现简单，但不可信。
- 基于最后一次心跳暂停：不符合离线继续计时。
- 每次模型调用时判断：会遗漏无模型调用的提交和恢复操作。

## 后果

- 客户端必须处理网络延迟，并以服务端返回的剩余时间为准。
- 截止判断依赖数据库时钟，不依赖应用实例之间的时钟一致性。
- 超时扫描与提交共享同一行锁，短时锁等待必须纳入延迟监控；需要可观测的拒绝计数和扫描积压。

## 验证

- 覆盖 `server_now < deadline_at`、`server_now = deadline_at`、`server_now > deadline_at` 三个边界，截止瞬间必须拒绝。
- 固定时长测试：开始面试后 `deadline_at - started_at` 必须为 2400 秒。
- 修改客户端时钟和 `client_submitted_at` 不影响判定。
- 断开后恢复仍使用原 `deadline_at`，不回退终态，不重置计时。
- 超时扫描与提交并发测试：任一事务先获得面试行锁后，另一方只能看到提交后的状态；不得出现截止后仍接收回答。
- 验证截止判断使用数据库时钟，例如在测试中偏移应用进程时间或注入应用时钟，结果不变。
