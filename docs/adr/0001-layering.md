# ADR-0001：固定分层与依赖方向

| 项目 | 内容 |
| --- | --- |
| 状态 | `accepted` |
| 日期 | 2026-10-17 |
| 决策者 | 技术负责人 |
| 评审日期 | 2026-10-17 |
| 影响 | 全部应用模块 |

## 背景

项目包含 HTTP API、智能体循环、工具、LLM 调用和异步任务。如果不固定依赖方向，容易出现路由层直接装配 Prompt、工具直接访问数据库、LLM 模块感知业务权限等问题，导致测试困难、权限绕过和调用无法追踪。

## 决策

本项目遵循 `AGENTS.md` 的分层红线，固定依赖方向：

```text
api -> agent -> tools -> llm
```

- `api` 只处理协议、认证依赖和 DTO。
- `agent` 执行有界 plan -> act -> observe，并在其内部承载用例编排、事务边界、权限、幂等和公开响应裁剪。
- `tools` 封装单一外部或计算能力，通过 Pydantic 参数模型注册。
- `llm` 负责 SDK、重试、超时、trace 和脱敏。
- 反向 import、跨层直调和全局可变单例禁止。

用例编排放在 `agent` 层内部，不等同于新增跨层 `services` 层。仓储、对象存储和邮件等基础设施通过显式接口注入，不改变层间依赖方向。

依赖矩阵和 Worker 装配边界见[技术设计](../technical-design.md#2-总体架构)，实现时以该矩阵为静态检查依据。

## 替代方案

1. 路由直接调用模型和工具：实现快，但权限、预算、错误回灌和 trace 容易散落。
2. 使用 LangChain 等上层框架：抽象重，隐藏 Prompt、重试和 token 计数，不符合项目可控要求。
3. 仅按业务域分模块、不区分层次：前期简单，后期会出现共享基础设施和业务规则耦合。
4. 新增独立 `services` 层：职责更直观，但需要先修改 `AGENTS.md` 的分层红线和目录约定，不能在 ADR 中直接越过项目规则。

## 后果

- 每个能力需要先确定所属层，短期增加样板代码。
- 业务服务可单测，LLM 可 mock，权限和预算检查有明确落点。
- 新增模块必须说明依赖方向和是否引入反向调用。

## 验证

- 代码评审检查 import 图。
- CI 建立模块名到允许依赖的静态检查，至少覆盖 API 导入 LLM、tools 导入 agent 或 api、llm 导入业务模块三类反向依赖。
- 关键模块测试禁止通过 monkeypatch 绕过 trace、Registry 或权限服务。
- 首个工程骨架提交必须包含通过和失败两种依赖检查样例。
