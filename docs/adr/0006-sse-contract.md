# ADR-0006：问答使用可重连 SSE 事件流

## 背景

需求要求技术问答流式展示首段，同时最终结构、引用和延伸问题在结束时完整可获取。移动网络会断开，不能让断线导致重复调用模型或丢失最终答案。

## 决策

- 问答增量使用 `text/event-stream`。
- 事件类型为 `started`、`delta`、`evidence`、`completed`、`error`。
- 事件 `id` 是持久化到 PostgreSQL 的每请求单调递增序号，不是连接内临时计数；同一请求跨连接必须保持序号一致。
- 支持 `Last-Event-ID` 和 `after_seq` 重连，服务端从 PostgreSQL 事件记录中补发序号更大的事件。
- 每条 SSE 事件的持久记录至少包含 `qa_request_id`、`seq`、`event_type`、`payload`、`created_at`；`UNIQUE (qa_request_id, seq)` 保证序号不重复。
- Redis 只能缓存已持久化事件，不能成为事件游标、终态或最终答案的唯一来源；清空 Redis 后仍可从 PostgreSQL 重建游标和终态。
- `delta` 只用于展示，最终答案以 `completed` 和持久化记录为准。
- `completed` 与 `error` 互斥，同一请求只能有一个终态事件，且每个终态事件最多出现一次；`error` 携带稳定错误码和可重试性。
- 服务端先在持久化事务中写入最终结构化结果和终态事件，再发送 `completed`；不能在结果提交前向客户端声明完成。
- 连接断开不取消服务端任务，也不重置游标；重连只补发事件，不重新执行检索、模型调用或重复消耗预算。
- 重复投递由客户端按事件 ID 去重；服务端不得因重连生成新的业务事件或改变终态。

## 替代方案

- 一次性 JSON 响应：无法满足首段流式。
- WebSocket：双向能力强，但本场景主要是单向事件，运维和代理复杂度更高。
- 轮询任务状态：实现简单但延迟和请求开销较高。

## 后果

- 需要持久化事件表、序号唯一约束、清理策略和可重建的终态查询。
- 客户端必须能处理重复事件，并按 `id` 去重；同一请求的终态以持久化记录为准。
- SSE 连接数和超时需纳入限流和监控。

## 验证

- 首段、完成、失败和空结果。
- 同一请求跨连接的事件序号连续且不回退；`Last-Event-ID` 和 `after_seq` 都只补发更大序号。
- 断开后重连不新增模型调用、不重复扣减检索或 token 预算。
- 重复 ID、跨用户访问和乱序网络投递。
- `completed` 与 `error` 互斥，且每个终态最多一次。
- 最终结构化结果在发送 `completed` 前已可从 PostgreSQL 读取。
- 清空 Redis 后仍能重建游标、终态和最终结果。
