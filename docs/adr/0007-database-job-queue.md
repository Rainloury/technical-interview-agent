# ADR-0007：P0 使用 PostgreSQL 任务表作为异步队列

| 项目 | 内容 |
| --- | --- |
| 状态 | `accepted` |
| 日期 | 2026-10-17 |
| 决策者 | 项目负责人 |
| 评审日期 | 2026-10-17 |
| 影响 | 异步任务、部署、可靠性 |

## 背景

简历分析和评分需要异步执行，项目当前处于 MVP 阶段。新增 Redis Streams、RabbitMQ 或云队列会增加部署、重试、可观测性和本地开发复杂度。

## 决策

- P0 使用 PostgreSQL `async_jobs` 表。
- Worker 使用 `FOR UPDATE SKIP LOCKED` 领取任务。
- 每次领取必须在同一事务中写入 `lease_owner`、单调递增的 `fencing_token` 和 `lease_until`；崩溃后由新租约重新领取。
- 成功、失败和租约续期写入必须同时校验当前 `lease_owner` 与 `fencing_token`；条件不满足时拒绝写入，旧 Worker 不得覆盖新租约。
- `fencing_token` 每次领取递增，不能由 Worker 自行生成或回退；租约过期不等于旧 Worker 自动获得写入权。
- 重试使用持久化次数、可重试标记和指数退避，超过上限进入死信。
- 任务幂等键和业务唯一约束是最终防重保护；租约与 fencing token 解决并发执行，不替代幂等。
- Worker 循环受最大运行时间、关闭信号和并发上限控制。

## 替代方案

- Redis Streams：吞吐更高，但增加消费者组和持久化运维。
- RabbitMQ：成熟，但首版部署和测试成本更高。
- 云托管队列：减少运维，但增加供应商绑定和本地模拟复杂度。

## 后果

- 数据库同时承担业务事实和任务租约，需要监控锁竞争、租约过期和表增长。
- 首版部署简单，测试可以固定同一数据库事务边界。
- 如果队列吞吐成为瓶颈，再以新 ADR 评估专用消息队列。

## 验证

- 多 Worker 并发领取同一任务时只有一个成功，且写入正确 `lease_owner`、递增 `fencing_token` 和 `lease_until`。
- Worker 崩溃、租约过期、新 Worker 接管和租约续期。
- 旧 Worker 在租约被接管后提交成功或失败结果，写入被 fencing 条件拒绝。
- 旧 Worker 续期失败后停止业务写入；过期租约不能复活。
- 死信、退避和任务清理。
- 任务重放不产生重复评分或错题，幂等键与业务唯一约束仍独立生效。
