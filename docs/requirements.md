## 1. 背景与目标

### 1.1 背景

求职者在准备技术面试时，通常面临以下问题：

- 简历中的技能和项目经历难以快速转化为有针对性的面试题。
- 遇到单个技术问题时，只能得到零散答案，缺少原理、工程实践和延伸追问。
- 缺少可重复的模拟面试、客观评分、错题沉淀和针对性复习闭环。

本项目构建一个技术面试智能体，面向准备后端、前端或全栈技术岗位的求职者，围绕简历出题、检索增强问答和有界追问式模拟面试提供结构化服务。

### 1.2 产品目标

1. 根据用户简历生成与经历相关、覆盖合理且可解释的面试题。
2. 对用户输入的技术面试题执行检索增强问答，给出有证据支撑的结构化回答，并延伸相关技术问题。
3. 通过模拟面试完成提问、回答、评分、分支追问、错题收集和薄弱知识点反馈闭环。
4. 对模型输出执行可校验的结构约束、事实边界和可观测性要求，降低幻觉与不可控行为。

### 1.3 成功指标

以下指标用于上线后评估产品效果。目标值在试点阶段确定，但指标口径和最低质量门槛需随 MVP 基线一并验证：

| 指标 | 定义 |
| --- | --- |
| 简历任务完成率 | 成功完成解析、分析和出题的上传任务占比 |
| 面试题采纳率 | 用户未删除、未跳过或明确保留的题目占比 |
| 问答有效率 | 用户未重新提问、未标记无帮助的回答占比 |
| 检索回答支持率 | 关键事实能够关联检索证据，或明确标注为模型知识的回答占比 |
| 评分一致性 | 同一回答在重复评分中的分数波动范围 |
| 错题命中率 | 用户确认为有效错题的记录占系统生成错题的比例 |
| 追问链完成率 | 高分触发追问后，用户完成追问回答和评分的次数占比 |
| 薄弱点命中率 | 用户确认需要加强的知识点占系统反馈薄弱点的比例 |
| 闭环完成率 | 完成模拟面试并查看错题和强化知识点反馈的会话占比 |
| 端到端延迟 | 各异步任务从提交到可查看结果的耗时 |
| 单任务模型成本 | 各业务流程的模型调用、token 与检索成本 |

## 2. 范围

### 2.1 MVP 范围

- 上传 PDF 或 DOCX 简历。
- 简历文件上限为 10 MB、最多 10 页；不解析扫描件。
- 提取简历文本并分析技能、项目经历、职责、成果和潜在缺口。
- 基于简历分析结果生成面试题、考察点和隐藏参考答案。
- 用户输入技术面试题，系统检索“官方技术文档精选 + 项目自建题库”，返回带证据的回答和延伸问题。
- 模拟面试支持后端、前端、全栈三个方向，用户在创建面试时选择其中一个方向。
- 创建模拟面试，按主问题和追问逐轮提问并接收用户回答。
- 对主问题和追问的回答进行结构化评分，按阈值判断是否通过。
- 低分结束当前追问链，并将未通过轮次写入错题集。
- 高分继续生成相关技术追问，每条追问链最多 2 层追问、最多 3 次回答；整场面试由服务端在 40 分钟到达时硬截止。
- 面试结束后向用户反馈错题、参考答案、失分原因和需要强化的知识点。
- 支持邮箱密码自助注册、登录、退出、服务端会话撤销和邮件找回密码。

### 2.2 暂不包含

- 模型训练或微调。本文中的“强化知识点”指复习建议，不指训练模型。
- 通用闲聊。
- 自动代替用户投递简历或联系招聘方。
- 自动执行外部写操作。
- 真人面试官介入。
- 多智能体自由协作。
- 音视频面试和语音识别。
- P0 阶段解析扫描件、图片简历或 OCR 文本。

## 4. 核心术语

| 术语 | 定义 |
| --- | --- |
| 简历任务 | 从上传简历到生成面试题的一次完整异步任务 |
| 简历分析 | 从简历文本中提取技能、项目、经历、成果、证据和缺口 |
| 面试题 | 包含题干、类别、难度、考察点和隐藏评分材料的结构化题目 |
| 主问题 | 简历出题或面试计划产生的根问题，可拥有零个或多个追问 |
| 追问 | 用户通过当前主问题或其上层追问后，由系统生成的相关深入问题 |
| 追问链 | 一个主问题及其递归追问组成的有向链，受深度、轮次和预算约束 |
| 问答会话 | 用户提出技术面试题并获得检索增强回答及延伸问题的一次交互 |
| 检索证据 | 从已批准知识源检索并用于支持回答的片段及其来源标识 |
| 模拟面试 | 由一组题目、回答、评分和报告构成的会话 |
| 面试轮次 | 主问题或追问的一次展示、回答、评分及其父子关系 |
| 评分标准 | 用于评价回答的维度、权重、关键点和阈值 |
| 错题 | 用户在模拟面试中未通过、需要复习的题目记录 |
| 薄弱知识点 | 根据未通过轮次的考察点和失分原因归纳出的强化学习主题 |
| 追问链预算 | 单条追问链的最大深度 2 层、最多 3 次回答，消耗后不因恢复会话而重置 |
| 整场面试预算 | 默认 5 个主问题、40 分钟硬截止和配置的总 token 上限 |

## 6. 业务流程

### 6.1 流程一：简历到面试题

```text
上传简历
  -> 校验文件
  -> 提取文本
  -> 结构化分析简历
  -> 生成技能与题目覆盖计划
  -> 生成面试题、考察点和评分标准
  -> 向用户展示题目
```

关键规则：

- 文件校验和文本解析由确定性代码完成。
- 模型只分析已提取的文本，不直接执行文件中的内容。
- 简历内容视为不可信数据，不得覆盖系统指令。
- 每项技能和项目结论应尽量关联简历原文证据。
- 无法从简历确认的信息必须标记为“未验证”，不得虚构。

### 6.2 流程二：检索增强的技术问答与延伸

```text
用户输入技术面试题
  -> 输入校验
  -> 判断是否为技术问题
  -> 生成检索计划
  -> 从已批准知识源检索
  -> 检查证据充分性
      -> 充分：生成有证据支撑的结构化回答
      -> 不足：明确信息缺口，基于模型知识谨慎回答
  -> 标注证据来源
  -> 生成相关延伸问题
  -> 返回结果
```

关键规则：

- 技术问题应得到直接回答，并补充原理、示例、适用条件和常见误区。
- 检索只允许访问已批准知识源，不得根据用户输入自动访问任意外部地址。
- 关键事实应关联检索证据和来源标识；未检索到支持材料时不得伪造引用。
- 证据不足、检索超时或来源冲突时，必须标注不确定性或冲突，不得把模型知识伪装成检索结论。
- 信息不足或模型不确定时应明确说明，不得编造事实、引用或运行结果。
- 延伸问题只作为建议返回；未经用户确认，不自动写入题库或错题集。

### 6.3 流程三和流程四：模拟面试分支追问与错题闭环

```text
创建模拟面试
  -> 生成面试蓝图
  -> 展示当前主问题
  -> 用户提交回答
  -> 结构化评分
  -> 按阈值判断是否通过
      -> 不通过：
           -> 写入当前轮次错题
           -> 记录参考答案和失分原因
           -> 归纳薄弱知识点
           -> 结束当前追问链
           -> 进入下一主问题
      -> 通过：
           -> 判断追问链是否达到深度或预算上限
               -> 未达到且总分 >= 85：生成相关技术追问
                   -> 生成成功：用户回答
                                -> 回到结构化评分
                   -> 生成失败：按失败类型重试或结束追问链
               -> 未达到且总分 70–84：结束当前追问链
               -> 用户选择跳过或主动结束：结束当前追问链
               -> 已达到：结束当前追问链
                         -> 进入下一主问题
  -> 完成全部题目
  -> 生成面试报告
  -> 返回错题、参考答案、失分原因和强化知识点
```

关键规则：

- 同一时刻只向用户展示当前题目。
- 参考答案和评分标准不得在用户回答前泄露。
- 评分明细由模型生成，加权总分和评分分段由确定性代码计算。
- 答案是否通过、是否触发追问由配置阈值决定，不交给模型自由判断。
- 总分 `<70` 不通过；`70–84` 通过但不追问；`>=85` 通过并进入追问。
- 任一关键事实错误或严重安全错误直接判定不通过，不受总分影响。
- 高分只触发“生成下一追问”分支，不得绕过评分和循环上限。
- 每个追问轮次必须重新评分；上层回答通过不代表下层追问自动通过。
- 单条追问链最多 2 层追问、最多 3 次回答；整场面试默认 5 个主问题、40 分钟硬截止，并受 token 预算约束。
- 追问达到上限、主题覆盖充分、无法生成有效延伸或用户主动结束时，结束当前追问链并推进到下一主问题。
- 追问必须与上层回答和当前主题相关，禁止为了延长会话而重复或泛化提问。
- 用户可以在追问阶段跳过当前追问或主动结束当前追问链，已提交轮次结果保持不变。
- 每个面试轮次只允许提交一次；错题重练必须在面试结束后作为独立记录进行。
- 错题、参考答案和详细评分在整场面试结束后统一展示。
- 错题写入必须幂等，重复提交或重试不得产生重复记录。
- 薄弱知识点根据失败轮次的考察点和失分原因归纳，并保留来源轮次以便追溯。
- 即使单题评分失败，也应保留面试会话并提供恢复或结束路径。

## 8. 状态模型

### 8.1 简历任务状态

```text
uploaded
  -> extracting
  -> analyzing
  -> generating_questions
  -> completed

任一处理阶段 -> failed
failed -> retry_created（创建新任务）
completed -> source_deleted（用户单独删除原始简历）
```

状态迁移必须校验合法性。已进入终态的任务不得被并发请求改写为其他状态；`source_deleted` 仅保留脱敏分析、题目和相关结果，不保留原始文件。

### 8.2 模拟面试状态

```text
created
  -> in_progress
  -> completed

created 或 in_progress -> cancelled
in_progress -> timed_out
in_progress -> failed（不可恢复错误）
```

每场面试固定保存主问题数量、服务端截止时间、总 token 和单条追问链预算。进入 `in_progress` 时启动 40 分钟计时，中断、离线或恢复期间继续计时；截止后进入 `timed_out` 并停止接受新回答。提前结束或超时不得自动将未回答题目写入错题集；已按时提交轮次的反馈在整场结束后统一解锁。

### 8.3 面试轮次状态

```text
pending
  -> awaiting_answer
  -> scoring
  -> passed
      -> follow_up_pending（生成子追问）
      -> branch_completed（结束当前追问链）
  -> failed
      -> wrong_book_recorded
      -> weak_point_recorded
      -> branch_completed

scoring -> scoring_failed
scoring_failed -> scoring（有限重试）
```

父轮次与子追问通过 `parent_turn_id` 关联。每个子追问都是独立面试轮次，必须独立提交回答和评分。每轮只接受一次回答；`passed` 后再按分数分段决定是否生成子追问。

### 8.4 面试追问上下文状态

```text
awaiting_answer
  -> scoring
  -> passed
      -> generating_follow_up
          -> awaiting_answer（总分 >= 85、生成成功且预算未耗尽）
          -> completed（达到深度、轮次、token 或时长上限）
          -> follow_up_failed（生成超时、重复或无关）
              -> generating_follow_up（有限重试）
              -> completed（重试耗尽）
  -> failed
      -> completed（结束当前分支）

awaiting_answer、scoring、generating_follow_up 或 follow_up_failed -> cancelled（用户结束面试）
awaiting_answer、generating_follow_up 或 follow_up_failed -> paused（支持暂停时）
awaiting_answer -> branch_completed（用户跳过或主动结束当前追问链）
paused -> awaiting_answer（恢复后使用剩余预算）
```

该状态描述一个追问链上下文的推进过程，主问题和追问轮次自身仍使用 8.3 的轮次状态。每条追问链预算为最多 2 层追问、最多 3 次回答；整场面试默认 5 个主问题和 40 分钟硬截止。追问上下文必须持久化当前深度、已用轮次、token 和服务端截止时间，恢复时不得重置预算。倒计时以服务端时间为准，客户端时间只用于展示。

### 8.5 错题状态

```text
active
  -> reviewing
  -> mastered

active 或 reviewing -> archived
```

状态流转为 P1 功能；MVP 至少需要 `active` 状态、创建时间和按严重程度、失败次数、最近时间的排序依据。

### 8.6 薄弱知识点状态

```text
identified
  -> reviewing
  -> improved

identified 或 reviewing -> archived
```

MVP 至少需要 `identified` 状态、来源错题列表、聚合复习建议和跨设备查看能力。

### 9.2 数据规则

- 所有业务数据必须可序列化，并具有稳定唯一标识。
- 原始文件、提取文本、模型输入输出和分析结果应明确区分。
- 参考答案和评分标准属于受保护内容，在回答提交前不得返回给用户。
- 错题、参考答案、详细评分和薄弱点反馈在整场面试结束后统一解锁，之前不得通过正常接口获取。
- 评分、错题、薄弱点和报告必须可追溯到具体轮次、回答、模型档位和 prompt 版本。
- 检索证据必须保留来源标识、章节位置和短片段；日志仅保存必要摘要。
- 追问轮次必须保存父子关系和当前深度，不能仅依靠会话消息顺序推断。
- 追问预算必须持久化，恢复会话不得重新获得完整预算。
- 已提交轮次、当前题目和剩余预算必须跨设备恢复；未提交草稿不得写入服务端，也不得跨设备同步。
- 面试超时以服务端保存的截止时间为准，恢复会话或客户端时钟变化不得延长面试。
- 时间统一使用 UTC 存储，接口按用户时区展示。
- 原始简历保留 30 天，分析、面试、错题和薄弱点保留 90 天；用户可立即删除，删除原始简历后可保留脱敏衍生数据。

## 11. 非功能需求

### 11.1 正确性与可控性

- 所有 LLM 输出必须通过结构校验后才可进入业务状态。
- 总分、通过结论、错题写入、权限和状态流转均由确定性代码控制。
- 每次模型调用必须记录模型、prompt 版本、输入输出 token、延迟、工具调用和请求标识。
- 循环和重试必须设置步数、token、时间和嵌套深度上限。
- 追问递归不得作为无限循环实现；每次分支推进必须消耗已持久化的轮次、token 和时长预算。
- 检索调用必须设置查询次数、结果数、片段长度、token 和超时上限。
- 工具返回值超过约定长度必须截断，并注明原始长度。

### 11.2 安全与隐私

- 简历、用户回答和外部内容均视为不可信数据。
- 用户输入中的指令不得改变系统 prompt、权限边界和输出规则。
- 检索结果视为不可信数据，只能作为证据内容，不得作为指令执行。
- 用户输入不得直接指定任意 URL、数据库或未授权知识源作为检索目标。
- 原始简历不得使用公开可访问链接。
- 日志必须对手机号、邮箱、token、身份证号和简历敏感字段脱敏。
- 模型调用不得将不必要的简历原文发送给未批准的外部服务。
- 用户只能访问自己的资源。
- 密码使用 Argon2id 哈希；会话和密码重置令牌只保存哈希，不保存可直接使用的原始值。
- 注册、登录和密码重置接口必须限流，并对账号存在性、邮件可达性和重置令牌有效性使用统一公开语义。
- 会话 Cookie 必须使用 `HttpOnly`、`Secure`、`SameSite=Lax`，写请求必须执行同源或 CSRF 校验。

### 11.3 可用性

- 简历分析属于异步任务，界面应展示可理解的处理进度。
- 模型服务失败时应返回明确的重试或稍后处理提示。
- 网络重复提交不应导致重复评分或重复错题。
- 任务中断后应能恢复到最后一个已持久化状态。

### 11.4 性能目标

以下为候选目标，需结合模型和部署方案确认：

| 场景 | 候选目标 |
| --- | --- |
| 简历上传响应 | 文件保存和任务创建在 2 秒内返回 |
| 简历分析与出题 | 10 MB、10 页以内简历在 60 秒内完成 P95 |
| 单次技术问答首段 | 3 秒内返回首段内容 P95 |
| 单次技术问答完成 | 20 秒内完成 P95（含证据引用） |
| 单次检索 | 3 秒内完成 P95，超时后进入证据不足分支 |
| 单题评分 | 15 秒内完成 P95 |
| 单次追问生成 | 10 秒内完成 P95 |
| 单条追问链 | 最多 2 层追问、3 次回答，且受总 token 预算约束 |
| 完整模拟面试 | 默认 5 个主问题、服务端 40 分钟硬截止，且受总 token 预算约束 |
| 错题列表查询 | 1 秒内完成 P95 |

### 11.5 可观测性

- 每个用户任务具有贯穿上传、解析、模型调用、评分和错题写入的请求标识。
- 记录任务失败阶段和可重试性。
- 记录用户账号与请求标识的关联，但日志不记录登录凭据或简历正文。
- 提供聚合指标：任务量、成功率、延迟、token 成本、检索命中率、评分失败率、错题写入失败率、追问链终止原因分布和数据删除到期执行结果。
- 运维日志不得包含完整简历、完整用户回答或密钥。

| AC-31 | 知识源发布新版本 | 新请求使用新版本；历史问答仍保留生成时的知识源版本和证据 |

| AC-41 | 用户提交一轮面试回答 | 接口返回 `202`、已接收和中性进度，不包含分数、通过结论、失分点、参考答案或追问依据；整场结束后报告才返回评分 |
| AC-42 | 用户等待评分和下一题 | 页面只展示中性流程状态、主问题完成数、剩余题数和剩余时间；不展示通过趋势、预测分数、关键错误提示或追问触发判断 |
| AC-43 | 用户结束当前追问链与整场面试 | P0 可结束当前追问链并进入下一主问题；整场提前结束不提供入口；跳过、结束追问链和结束整场分别记录原因，不互相覆盖 |
| AC-44 | 用户删除原始简历后查看历史证据 | 证据摘要不超过 200 个字符，只展示脱敏摘要、能力标签、题目关联和“来源已删除”；原文引用、页码定位、文件名和可恢复正文的上下文均不可见 |
| AC-45 | 删除、到期清理和安全事件生成审计 | 审计仅包含允许的元数据，资源标识不可逆；记录在 365 天后被删除或不可逆匿名化；任何用户正文、答案、证据原文或凭据均不出现 |

### 12.2 模型行为评测

评测用例至少覆盖：

- 简历关键事实抽取准确性。
- 题目与简历证据的相关性。
- 不同主题和难度的覆盖度。
- 技术回答的事实正确性和不确定性表达。
- 检索查询与知识源选择的相关性。
- 证据引用是否支持回答中的关键事实。
- 检索不足时是否正确表达不确定性。
- 延伸问题相关性。
- 高分追问与父回答的技术相关性。
- 追问链是否按深度、轮次、token 和时长条件正确终止。
- 薄弱知识点是否由实际失分原因支撑。
- 评分与参考答案的一致性。
- 边界分数和关键错误判定。
- prompt 注入、越权获取答案和敏感信息泄露。
- 同一输入的重复生成稳定性。

发布前的最低评测门槛：

| 门槛 | 最低要求 |
| --- | --- |
| 总体行为评测通过率 | >= 90% |
| 单个面试方向通过率 | >= 85% |
| 安全、越权、答案泄露和 prompt 注入类关键项 | 100% |
| 任一评测类别通过率 | >= 80% |
| 单场完整面试模型与检索成本 | P95 <= ¥3.00，按供应商标价计算 |

每次修改 prompt、评分规则或模型档位后，必须运行评测并与基线比较。通过率下降或成本上升超过 15% 时不允许合并；任何一项低于上表绝对门槛时也不得发布。

评测集至少包含每个面试方向 30 条用例（24 条核心主题、6 条边界或对抗场景）及 20 条共享安全与契约用例，总计不少于 110 条。每个方向的核心主题至少各覆盖 3 条用例。

### 12.3 单测与集成测试

- 文件类型、大小和损坏文件校验。
- 简历任务和面试状态机的合法与非法迁移。
- 追问链的递归分支、终止条件和预算恢复。
- 追问轮次父子关系及独立评分。
- 评分加权、阈值和关键错误规则。
- 错题和薄弱知识点幂等写入。
- 检索范围限制、结果截断和超时降级。
- 权限隔离。
- 注册、登录、退出、会话撤销和密码重置。
- 账号枚举、重置令牌重放与并发使用测试。
- 内部评分存在但回答提交公开 DTO 不返回受保护字段的契约测试。
- 模型调用超时、限流、结构化输出失败和有限重试。
- 日志脱敏和不可信内容包裹。

## 13. 发布边界

### 13.1 MVP P0

- PDF/DOCX 简历上传和异步处理。
- 简历上限 10 MB、10 页；扫描件和图片简历不支持。
- 登录账号、跨设备访问和用户数据隔离。
- 原始简历 30 天、衍生数据 90 天保留策略，以及用户立即删除能力。
- 简历结构分析及针对性出题。
- 默认 10 道题，难度分布 30%/50%/20%。
- 基于官方技术文档精选和项目自建题库的检索增强流式问答、证据引用和延伸问题。
- 检索不足时的模型知识标注和拒答策略。
- 支持后端、前端、全栈三个方向的模拟面试：5 个主问题、服务端 40 分钟硬截止、每条追问链最多 2 层追问和 3 次回答。
- 每个方向覆盖 8 个 P0 核心主题，并至少对 3 个主题进行设计取舍考察。
- 结构化评分、确定性通过判断、关键错误一票否决和错题自动收集。
- 70/85 分段规则：低于 70 不通过，70–84 通过但不追问，85 及以上通过并追问。
- 薄弱知识点提取、聚合排序和强化学习建议。
- 面试报告、完整追问树、错题详情和薄弱点反馈。
- 单轮只提交一次、已提交轮次跨设备恢复、本机草稿恢复、用户跳过/结束追问、整场面试结束后统一解锁反馈。
- 模型行为评测达到总体 90% 和方向 85% 的绝对门槛，且完整面试成本 P95 不超过 ¥3.00。
- 用户资源隔离、trace、输入输出结构校验、流式输出和基础安全测试。
- 邮箱密码自助注册、登录、退出、服务端会话撤销和邮件找回密码。

### 13.2 P1

- 用户修正简历分析结果。
- 题目筛选和出题原因展示。
- 可选目标岗位 JD 出题。
- 用户上传受控资料作为检索源。
- 面试暂停和提前结束。
- 按薄弱知识点筛选错题及人工修正分类。
- 错题状态、重练和导出。
- 评分一致性辅助校验。
- PDF 面试报告导出。

### 13.3 P2

- 个性化复习计划。
- 多轮学习趋势和长期能力画像。
- 语音面试。
- 团队题库和知识库管理。
- 多模型对比和自动路由。

## 14. 已确认决策基线

以下决策已于 2026-10-17 确认，作为 v1.5 MVP 需求基线。后续变更必须更新版本记录并重新评估验收场景。

| 编号 | 决策 |
| --- | --- |
| D-01 | 使用登录账号，支持跨设备访问历史记录。 |
| D-02 | 简历仅支持 PDF 和 DOCX，不支持扫描件或图片简历。 |
| D-03 | 简历上限 10 MB、最多 10 页。 |
| D-04 | 原始简历保留 30 天，分析与面试相关数据保留 90 天，并支持立即删除。 |
| D-05 | 首发支持后端、前端、全栈三个面试方向，由用户在创建模拟面试时选择。 |
| D-06 | 默认生成 10 道题，难度为简单 30%、中等 50%、困难 20%。 |
| D-07 | 默认 5 个主问题；每条追问链最多 2 层追问、3 次回答；整场 40 分钟。 |
| D-08 | 评分权重为正确性 35、技术深度 25、工程判断 20、完整性 10、表达 10。 |
| D-09 | 总分低于 70 不通过；70–84 通过但不追问；85 及以上通过并触发追问。 |
| D-10 | 关键事实错误或严重安全错误一票否决。 |
| D-11 | 每个面试轮次只提交一次；面试结束后可独立重练。 |
| D-12 | 错题、参考答案、详细评分和薄弱点在整场面试结束后统一展示。 |
| D-13 | 参考答案仅在整场面试结束后可见。 |
| D-14 | 可选目标岗位 JD 出题属于 P1。 |
| D-15 | P0 使用官方技术文档精选和项目自建题库；不接企业知识库或实时互联网搜索。 |
| D-16 | 问答回答在 P0 支持流式输出。 |
| D-17 | 允许删除原始简历，同时保留脱敏分析、错题和薄弱点。 |
| D-18 | PDF 面试报告导出属于 P1。 |
| D-19 | 官方文档精选月度审核，自建题库版本化导入。 |
| D-20 | 70/85 双阈值：低于 70 不通过，70–84 通过不追问，85 及以上追问。 |
| D-21 | 追问最多 2 层，用户可跳过或主动结束当前追问链。 |
| D-22 | 面试报告展示完整追问树并分别标记各轮结果，失败子轮次汇总为薄弱点。 |
| D-23 | 薄弱点按严重程度、失败次数、最近发生时间依次排序。 |
| D-24 | 向用户展示来源标题、章节位置和短证据片段。 |
| D-25 | P0 不接受任意 URL 或用户上传资料作为检索源；受限文件上传列入 P1。 |
| D-26 | 检索不足时允许谨慎回答并标注模型知识来源；不确定时拒答。 |
| D-27 | 整场面试由服务端在 40 分钟到达时硬截止；离线期间继续计时，截止后拒绝新提交，已接收回答继续评分，未作答轮次不写入错题。 |
| D-28 | 已提交轮次、当前题目和剩余预算跨设备恢复；未提交草稿仅保存在原设备本地，不写入服务端。 |
| D-29 | 后端、前端、全栈共享检索、出题和评分框架，按方向配置核心主题、知识源白名单、题型模板和评分锚点；全栈包含端到端集成主题。 |
| D-30 | 模型评测发布门槛为总体通过率 >= 90%、单方向 >= 85%、安全关键项 100%、任一类别 >= 80%；完整面试成本 P95 <= ¥3.00。 |
| D-31 | 每个方向定义 8 个 P0 核心主题，全部达到概念理解和场景应用，至少 3 个主题达到设计取舍深度；每场 5 个主问题至少覆盖 4 个不同主题。 |
| D-32 | 账号使用邮箱密码方案，密码以 Argon2id 哈希；允许自助注册，注册统一返回中性受理结果且不建立会话；登录是唯一会话签发入口，会话由服务端签发并可撤销；邮件找回密码纳入 P0，重置令牌只保存哈希且成功后撤销全部旧会话。 |
| D-33 | 回答提交公开响应只包含 `202`、已接收和中性进度；评分写入内部状态，分数、通过结论、失分点和追问依据在整场结束后随报告统一解锁。 |
| D-34 | 面试进行中只展示中性流程信息，可包含已提交轮次、主问题完成数、剩余题数、当前追问链状态和剩余时间；不展示通过趋势、预测分数、关键错误提示或追问依据。 |
| D-35 | P0 只提供结束当前追问链；“提前结束整场”保留到 P1，使用独立操作和二次确认；跳过、结束追问链和结束整场分别记录原因。 |
| D-36 | 删除原始简历后只保留脱敏证据摘要、能力标签、题目关联和“来源已删除”标识；每条摘要最多 200 个字符，不得保留原文引用、页码定位、文件名或可恢复正文的上下文。 |
| D-37 | 审计仅记录操作类型、资源类型内部枚举、哈希化资源标识、结果、时间和请求 ID，保留 365 天后删除或不可逆匿名化，不记录任何用户业务内容。 |
