## 1. 审批规则

### 1.1 必须审批的变更

- 新增、删除或改变 P0/P1/P2 范围。
- 新增或修改 `FR-*`、`AC-*`、产品状态和公开接口的可观察行为。
- 改变评分、阈值、时间预算、追问预算或方向覆盖口径。
- 改变用户看到的内容、受保护内容解锁时机或错误提示语义。
- 改变数据保留、删除、审计、权限或跨设备语义。
- 引入会影响用户使用方式的账号、登录或身份方案。

### 1.2 可以由技术方案决定的事项

- 在不改变需求和接口语义的前提下选择数据库结构、索引和事务边界。
- 选择内部模块划分、类型、日志字段、重试机制和测试组织方式。
- 采用已冻结需求对应的推荐实现，例如服务端截止时间校验、幂等键和行级锁。

### 1.3 状态定义

| 状态 | 含义 | 是否可写入基线 |
| --- | --- | --- |
| `proposed` | 已提出，尚未进入审批 | 否 |
| `awaiting_approval` | 已完成影响分析，等待项目负责人明确批准 | 否 |
| `approved` | 已获得显式批准 | 是 |
| `rejected` | 明确不采用 | 否 |
| `superseded` | 被后续批准项替代 | 否 |

### 1.4 审批信息格式

每次提交需求决策时，至少说明：

1. 决策编号和问题。
2. 推荐方案和选择理由。
3. 备选方案及主要代价。
4. 受影响的需求、验收、文档和实现。
5. 不决策时会阻塞什么。

批准时使用明确表述，例如“批准 `DR-01` 和 `DR-02`”或“`DR-01` 选择方案 B”。含糊确认不视为批准。

### DR-01 账号注册与登录方式

| 项目 | 内容 |
| --- | --- |
| 状态 | `approved` |
| 审批日期 | 2026-10-17 |
| 影响 | 账号创建、登录页、会话管理、安全实现和首切片范围 |
| 审批结论 | 三项均按推荐方案执行 |

已批准内容：

- 方案 A：邮箱密码注册登录，密码使用 Argon2id 哈希。
- 允许用户自助注册；注册接口需要限流和防账号枚举。
- 注册统一返回中性 `202 Accepted`，不建立会话、不设置 Cookie；登录是唯一会话签发入口。
- 登录成功后签发服务端可撤销会话 Cookie，属性为 `HttpOnly`、`Secure`、`SameSite=Lax`。
- 首版不接第三方 OAuth，不使用短信验证码。
- 邮件找回密码纳入 P0；一次性重置令牌只保存哈希、短时有效、使用后失效，并撤销该账号全部旧会话。
- 邮件发送失败不阻塞注册和登录，但界面必须提供可重试的恢复提示。

### DR-02 单轮回答提交后的用户可见响应

| 项目 | 内容 |
| --- | --- |
| 状态 | `approved` |
| 审批日期 | 2026-10-17 |
| 影响 | 面试接口、SSE/轮询、面试页反馈、受保护内容边界 |
| 审批结论 | 方案 A |

已批准内容：

- 评分结果写入内部状态；整场进入终态且已接收轮次全部评分完成后，通过报告接口统一解锁。
- `FR-INT-005` 的“返回”指内部结构化评分结果，不要求在提交接口向用户公开。

## 4. 首个用户可见切片

### DR-07 首个用户可见切片与前端工程

| 项目 | 内容 |
| --- | --- |
| 状态 | `approved` |
| 提出日期 | 2026-10-17 |
| 审批日期 | 2026-10-17 |
| 影响 | 首个用户可见行为、前端工程、认证页面、工作台、历史分页、安全测试和交付顺序 |
| 审批结论 | 方案 A |
| 需求依据 | `FR-AUTH-001` 至 `FR-AUTH-008`、`FR-HIS-001`、`FR-HIS-002`、`FR-HIS-004`、`AC-38` 至 `AC-40` |

#### 决策问题

“账号 -> 工作台 -> 空状态”是否作为首个可演示纵向切片，并在同一交付中建立前端工程、认证页面、工作台摘要与历史分页入口？

#### 推荐方案

方案 A：以一个纵向切片交付完整的账号进入路径和工作台入口。

1. 前端技术栈采用 React + TypeScript + Vite；路由采用 React Router；服务端状态和数据请求采用 TanStack Query。
2. 页面范围包括登录、注册、找回密码、重置密码、工作台，以及最近任务为空时的空状态。
3. 同一切片包含工作台摘要、最近面试摘要和历史分页入口；分页优先复用 `GET /api/v1/history`，不另外发明一套前端专用历史模型。
4. 单元与组件测试采用 Vitest + Testing Library + MSW；关键用户旅程采用 Playwright 覆盖注册、登录、工作台、退出和密码重置。
5. 所有改变状态的写请求使用显式 CSRF 令牌，并与 Origin/Referer allowlist 共同防御；不把 `SameSite=Lax + Origin` 作为唯一保护。
6. 前端只保存非敏感的服务端状态缓存；会话 Cookie 保持 `HttpOnly`、`Secure`、`SameSite=Lax`，不进入 localStorage、URL 或日志。
7. 接口继续遵循 [接口契约](./api-contract.md)：注册和找回密码返回中性结果，登录是唯一会话签发入口，越权与不存在资源使用一致公开结果。

选择理由：

- 切片能够独立演示“游客进入、注册、登录、看到自己的空工作台和分页历史入口”的完整用户路径。
- React、TypeScript 和 Vite 与现有 HTTP API 解耦，不改变后端 `api -> agent -> tools -> llm` 分层。
- TanStack Query 统一处理会话过期、重试、缓存失效和加载状态，减少手写请求状态造成的权限提示漂移。
- 显式 CSRF 令牌为 Cookie 会话提供独立于浏览器默认行为的服务端校验，便于写请求安全测试和后续扩展。
- 历史分页与工作台处于同一信息架构，但使用独立接口和稳定游标，避免把“全部历史”塞进工作台首屏响应。

#### 备选方案

| 方案 | 做法 | 主要代价 |
| --- | --- | --- |
| B | 只交付登录和工作台空状态，历史分页与注册、找回密码后移 | 首个切片无法闭合已批准认证范围，需再拆一次审批且不能完整验证 AC-38 至 AC-40 |
| C | 使用单体模板或后端渲染，不建立独立前端工程 | 与后续工作台、面试和报告交互复用性较差，前端测试与无障碍验证边界不清晰 |
| D | 采用 Next.js 或 Remix 等服务端渲染框架 | 当前没有 SEO、服务端渲染或边缘部署需求，增加运行时、构建和部署复杂度 |
| E | 只依赖 `SameSite=Lax` 和 Origin/Referer 校验，不增加显式 CSRF 令牌 | 对同站子域、配置误放行和未来跨域部署的防御较弱，安全测试难以形成独立校验点 |

#### 不在本决策内

- 简历上传、技术问答、模拟面试和报告页面。
- 视觉品牌定稿、第三方 OAuth、短信验证码、账号设置和 PDF 导出。
- 新增后端业务范围；本切片只实现已批准的认证与历史入口需求。
- 生产邮件供应商选型；本地可用可控的测试邮件适配器，真实投递需在切片实现时补充配置。

#### 批准后的交付边界

- 新建 `web/`，并保持前端独立构建、测试和部署配置。
- 实现账号进入路径、工作台摘要、历史分页和空状态。
- 增加 Cookie/CSRF、账号枚举、越权、会话失效和分页游标的接口与浏览器测试。
- 同步 API 契约、技术设计、威胁模型、开发流程和测试矩阵。
- 完成真实模型 `G4A` 验收仍作为核心能力基座的独立条件；`DR-07` 批准不等于宣布 `G4A` 已通过。

## 5. 审批后处理

获得批准后，按以下顺序执行：

1. 将决策状态更新为 `approved`。
2. 更新 `docs/requirements.md` 的 `FR-*`、`AC-*`、决策基线和版本记录。
3. 更新产品方案和接口契约。
4. 同步技术设计、数据模型、ADR 和测试计划。
5. 在开发流程中解除对应阻塞项。

后续新增或修改用户可见行为仍按本文件规则审批，不得以既有实现替代新的需求决策。
