## 1. 审批规则

### 1.1 必须审批的变更

- 新增、删除或改变 P0/P1/P2 范围。
- 新增或修改 `FR-*`、`AC-*`、产品状态和公开接口的可观察行为。
- 改变评分、阈值、时间预算、追问预算或方向覆盖口径。
- 改变用户看到的内容、受保护内容解锁时机或错误提示语义。
- 改变数据保留、删除、审计、权限或跨设备语义。
- 引入会影响用户使用方式的账号、登录或身份方案。

### 1.2 可以由技术方案决定的事项

- 在不改变需求和接口语义的前提下选择数据库结构、索引和事务边界。
- 选择内部模块划分、类型、日志字段、重试机制和测试组织方式。
- 采用已冻结需求对应的推荐实现，例如服务端截止时间校验、幂等键和行级锁。

### 1.3 状态定义

| 状态 | 含义 | 是否可写入基线 |
| --- | --- | --- |
| `proposed` | 已提出，尚未进入审批 | 否 |
| `awaiting_approval` | 已完成影响分析，等待项目负责人明确批准 | 否 |
| `approved` | 已获得显式批准 | 是 |
| `rejected` | 明确不采用 | 否 |
| `superseded` | 被后续批准项替代 | 否 |

### 1.4 审批信息格式

每次提交需求决策时，至少说明：

1. 决策编号和问题。
2. 推荐方案和选择理由。
3. 备选方案及主要代价。
4. 受影响的需求、验收、文档和实现。
5. 不决策时会阻塞什么。

批准时使用明确表述，例如“批准 `DR-01` 和 `DR-02`”或“`DR-01` 选择方案 B”。含糊确认不视为批准。

### DR-01 账号注册与登录方式

| 项目 | 内容 |
| --- | --- |
| 状态 | `approved` |
| 审批日期 | 2026-10-17 |
| 影响 | 账号创建、登录页、会话管理、安全实现和首切片范围 |
| 审批结论 | 三项均按推荐方案执行 |

已批准内容：

- 方案 A：邮箱密码注册登录，密码使用 Argon2id 哈希。
- 允许用户自助注册；注册接口需要限流和防账号枚举。
- 注册统一返回中性 `202 Accepted`，不建立会话、不设置 Cookie；登录是唯一会话签发入口。
- 登录成功后签发服务端可撤销会话 Cookie，属性为 `HttpOnly`、`Secure`、`SameSite=Lax`。
- 首版不接第三方 OAuth，不使用短信验证码。
- 邮件找回密码纳入 P0；一次性重置令牌只保存哈希、短时有效、使用后失效，并撤销该账号全部旧会话。
- 邮件发送失败不阻塞注册和登录，但界面必须提供可重试的恢复提示。

### DR-02 单轮回答提交后的用户可见响应

| 项目 | 内容 |
| --- | --- |
| 状态 | `approved` |
| 审批日期 | 2026-10-17 |
| 影响 | 面试接口、SSE/轮询、面试页反馈、受保护内容边界 |
| 审批结论 | 方案 A |

已批准内容：

- 回答提交接口只返回 `202 Accepted`、已接收状态和中性进度。
- 公开响应不返回分项分数、总分、通过结论、失分点、参考答案、评分标准或追问依据。
- 评分结果写入内部状态；整场进入终态且已接收轮次全部评分完成后，通过报告接口统一解锁。
- `FR-INT-005` 的“返回”指内部结构化评分结果，不要求在提交接口向用户公开。

## 4. 审批后处理

获得批准后，按以下顺序执行：

1. 将决策状态更新为 `approved`。
2. 更新 `docs/requirements.md` 的 `FR-*`、`AC-*`、决策基线和版本记录。
3. 更新产品方案和接口契约。
4. 同步技术设计、数据模型、ADR 和测试计划。
5. 在开发流程中解除对应阻塞项。

后续新增或修改用户可见行为仍按本文件规则审批，不得以既有实现替代新的需求决策。

## 5. 审批回执模板

项目负责人可使用以下格式批准：

```text
DR-03 选择方案 B。
批准 DR-04、DR-05、DR-06 推荐方案。
```
